# GRPO (Group Relative Policy Optimization)

Archetype’s GRPO module is intentionally small and explicit: it focuses on the **data artifacts** needed for a correct training step and keeps the “one obvious way” boundary between rollout, advantage computation, and gradient updates.

## The artifact contract (critical)

To train correctly, you must avoid retokenization. Rollouts must produce:

- `completion_token_ids`: the exact token IDs generated by the rollout engine
- `old_token_logprobs`: per-token logprobs under the behavior policy (the rollout policy)

Archetype provides rollout engines that emit this contract:

- `archetype.rl.grpo.rollout_transformers.TransformersTextRollout` (CPU-friendly dev)
- `archetype.rl.grpo.rollout_vllm.VllmTextRollout` (fast vLLM inference)

## Pipeline glue (Daft-native)

`archetype.rl.grpo.pipeline.build_grpo_rollouts_from_mc_dataset()` shows a complete Daft-native pattern:

- repeat each prompt K times (group size)
- rollout to get token IDs + logprobs
- compute reward
- compute group-relative advantages via window ops

## “Weights as data”

Training updates are expressed as “write a new checkpoint, return its path”.

`archetype.rl.grpo.train_udf.PytorchGrpoTrainer`:

- receives `weights_file` as a `daft.File`
- loads the checkpoint inside the worker
- runs forward/backward/step in PyTorch
- writes a new safetensors checkpoint to `output_path`
- returns metrics (including the new weights path)

This lets Daft distribute rollout/reward/advantage computation while keeping the gradient step consolidated (typically via `.into_partitions(1)`).
