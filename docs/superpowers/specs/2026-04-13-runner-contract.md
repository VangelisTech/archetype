# Archetype Runner Contract

## Goal

Define the bidirectional contract between **Archetype** (experiment lifecycle engine) and **Archetype Runner** (VM provisioning and agent execution service) so that the auto research loop can close end-to-end without tight coupling.

## Design Principles

1. **SQLite as the integration bus.** Both sides already use SQLite. No HTTP servers or message queues — disproportionate for single-machine deployment.
2. **Archetype models and decides; Runner materializes and executes.** (Carries forward from the v0.1 design spec.)
3. **Schema-first, not API-first.** The contract is table schemas and row lifecycles. Both sides read/write rows; neither calls the other directly.
4. **Components mirror contract tables.** ECS Components match the table shapes row-for-row, following the existing `Run` ↔ `agents` precedent.
5. **Runner is eval-blind.** Runner reports facts (commit hash, exit code, logs). Archetype interprets them.

## Data Files

Three SQLite files, each with a single clear owner:

| File | Writer | Reader | Path | Purpose |
|------|--------|--------|------|---------|
| `requests.db` | Archetype | Runner | `~/.archetype-runner/requests.db` | Run request queue |
| `state.db` | Runner | Archetype | `~/.archetype-runner/state.db` (existing) | Agent status + completion reports |
| `tapes/<run_id>.db` | Tapes proxy (in-VM) | Archetype | `~/.archetype-runner/tapes/<run_id>.db` | Trajectory data (tool calls, chat messages) |

Single-writer-per-file eliminates write contention. `requests.db` and `state.db` use WAL mode. Readers open read-only via SQLite URI mode (`?mode=ro`), matching the existing pattern in `loaders.py`.

**Polling model:** Runner polls `requests.db` for rows with `status = 'pending'`. Archetype polls `state.db` for status changes and new report rows. Both poll on a configurable interval (default 2 seconds).

**Ownership exception:** Runner's claim UPDATE on `requests.db` is the sole write Runner makes to that file. This is intentionally limited to a single atomic UPDATE on a specific row. All other writes to `requests.db` are Archetype's.

### Trajectory preservation

The tapes proxy inside each VM records all tool calls and chat messages to a local SQLite file during execution. This file must survive VM teardown:

1. Agent exits (success, crash, or timeout).
2. Runner copies the tapes SQLite out of the VM to `~/.archetype-runner/tapes/<run_id>.db`.
3. Runner writes `run_reports` row (commit hash, exit status, logs).
4. Runner cleans up the VM and workspace.

Step 2 must happen before step 4. This is a plain file copy — Runner does not parse or transform the trajectory data. The tapes proxy owns the schema; Archetype's trajectory loaders know how to read it.

## Schema: `requests.db` (Archetype → Runner)

### Table: `run_requests`

```sql
CREATE TABLE run_requests (
    request_id      TEXT PRIMARY KEY,         -- UUID, generated by Archetype
    experiment_name TEXT NOT NULL,             -- links to Experiment.name
    repo_url        TEXT NOT NULL,             -- git clone URL
    branch          TEXT NOT NULL,             -- branch to check out
    base_commit     TEXT NOT NULL DEFAULT '',  -- specific commit to start from ('' = branch HEAD)
    task            TEXT NOT NULL,             -- natural-language prompt for the agent
    harness         TEXT NOT NULL DEFAULT 'claude-code',
    timeout_sec     INTEGER NOT NULL DEFAULT 1800,  -- 30 min default
    metadata_json   TEXT NOT NULL DEFAULT '{}',     -- free-form user context
    status          TEXT NOT NULL DEFAULT 'pending', -- pending | claimed | rejected
    created_at      TEXT NOT NULL,             -- ISO-8601
    claimed_at      TEXT,                      -- set by Runner when claimed
    claimed_by      TEXT                       -- Runner instance ID (future multi-runner)
);
```

### Request lifecycle

1. Archetype writes a row with `status = 'pending'`.
2. Runner reads pending rows, picks one, atomically updates `status = 'claimed'`, sets `claimed_at` and `claimed_by`.
3. Runner creates a corresponding row in `state.db` `agents` table (with `request_id` set) and proceeds with VM provisioning.
4. If Runner cannot fulfill the request (no capacity, bad harness, etc.), it sets `status = 'rejected'`.

### Runner's obligations on claim

- Clone `repo_url`, check out `branch`.
- If `base_commit` is non-empty, `git checkout <base_commit>` after clone.
- Start the agent with the specified `harness`.
- Enforce `timeout_sec` as a hard wall-clock limit.
- Set `agents.request_id` to link the execution back to the request.

## Schema: `state.db` Extensions (Runner → Archetype)

### Existing table: `agents` (one new column)

```sql
ALTER TABLE agents ADD COLUMN request_id TEXT DEFAULT '';
```

When a run originates from a `run_requests` row, Runner sets `request_id` to match. For ad-hoc runs (started manually), `request_id` stays empty.

### New table: `run_reports`

```sql
CREATE TABLE run_reports (
    report_id     TEXT PRIMARY KEY,           -- UUID, generated by Runner
    agent_id      TEXT NOT NULL,              -- FK to agents.agent_id (= Run.run_id)
    request_id    TEXT NOT NULL DEFAULT '',   -- FK to run_requests.request_id
    exit_status   TEXT NOT NULL,              -- 'completed' | 'crashed' | 'timed_out'
    commit_hash   TEXT NOT NULL DEFAULT '',   -- git SHA produced by agent ('' if none)
    diff_stat     TEXT NOT NULL DEFAULT '',   -- e.g. "3 files changed, 47+, 12-"
    stdout_tail   TEXT NOT NULL DEFAULT '',   -- last N lines of stdout
    stderr_tail   TEXT NOT NULL DEFAULT '',   -- last N lines of stderr
    metadata_json TEXT NOT NULL DEFAULT '{}', -- wall time, token counts, etc.
    created_at    TEXT NOT NULL               -- ISO-8601
);
```

### Why a separate `run_reports` table?

The `agents` table is Runner's live status tracker, updated in-place as status changes. `run_reports` is an append-only record of what the agent produced, written once when the run finishes:

- Runner can update `agents.status` freely without preserving report fields.
- Archetype gets a clean, immutable record to ingest.
- Multiple reports per agent are possible (`report_id` is the PK, not `agent_id`).

### Runner's post-exit sequence

After the agent exits, Runner executes these steps in order:

1. Capture commit hash: `git -C <workspace_path> rev-parse HEAD`
2. Capture diff stat: `git -C <workspace_path> diff --stat <base_commit>..HEAD`
3. Copy tapes SQLite out of VM: `cp <vm_tapes_path> ~/.archetype-runner/tapes/<run_id>.db`
4. Write one row to `run_reports` with commit hash, exit status, and tail logs.
5. Update `agents.status` to terminal state (`stopped` or `crashed`).
6. Clean up VM and workspace.

Steps 1–4 must complete before step 6. If Runner crashes between steps, the incomplete state is recoverable: a missing report row with a present tapes file means "run finished but report wasn't written" — Archetype can detect this and re-derive the report from the tapes and git state.

## Separation of Concerns

### Archetype owns

| Responsibility | Notes |
|---------------|-------|
| Experiment lifecycle | Experiment component: pending → running → succeeded/crashed → kept/discarded |
| Run request creation | Writes to `requests.db` |
| Polling Runner state + reports | Reads from `state.db` (agents + run_reports) |
| Trajectory ingestion | Reads `tapes/<run_id>.db` files via existing trajectory loaders |
| Evaluation execution | Runs evals against the agent's commit |
| Result creation | Result component: opaque outputs, multiple per run |
| BranchHead comparison | User-defined comparison logic (scalar, Pareto, LLM judge) |
| Keep/discard decision | Advances BranchHead only on improvement |
| Next-request generation | Creates next RunRequest from current BranchHead |

### Runner owns

| Responsibility | Notes |
|---------------|-------|
| Polling `requests.db` | Picks pending requests, claims them |
| VM provisioning | masterblaster integration |
| Workspace cloning | Honors repo_url, branch, base_commit |
| Agent execution | Starts harness (claude-code, opencode, hermes) |
| Timeout enforcement | Hard wall-clock limit from `timeout_sec` |
| Commit-hash capture | `git rev-parse HEAD` before cleanup |
| Trajectory preservation | Copies tapes.db out of VM before cleanup |
| Report writing | Appends to `run_reports` in `state.db` |
| Workspace cleanup | After report is written and tapes are preserved |

### Tapes proxy owns

| Responsibility | Notes |
|---------------|-------|
| Trajectory recording | Tool calls, chat messages, streaming events |
| Schema definition | Tapes proxy defines the SQLite schema; Runner and Archetype do not |
| In-VM persistence | Writes to local SQLite during agent execution |

## Evaluation Pipeline

Entirely Archetype's responsibility. **Runner does not run evals.**

```
Run finishes
  → Runner copies tapes.db, writes run_reports row
  → Archetype ingests RunReport + trajectory data
  → If commit_hash is non-empty:
      → Archetype checks out the commit (clone + checkout)
      → Archetype runs eval(s): pytest, ruff, llm-judge, custom, etc.
      → Each eval produces a Result entity
  → Experiment loop reads Results for this run
  → Compares against BranchHead descriptor
  → If better: advance BranchHead, experiment → kept
  → If not: experiment → discarded
  → Create next RunRequest from current BranchHead.commit_hash as base_commit
```

**Why Runner does not run evals:**

1. Eval logic changes independently of execution.
2. Eval may need context Runner does not have (BranchHead state, historical Results).
3. Karpathy's principle: the comparison is the orchestrator's job.

**Exception:** Some eval data is most naturally captured inside the VM (test output, exit codes). Runner puts these in `run_reports.metadata_json` and `stdout_tail`/`stderr_tail`. Archetype decides what they mean.

## ECS Components

### `RunRequest`

Mirrors `run_requests` table. Archetype-side record of what was requested.

Fields: `request_id`, `experiment_name`, `repo_url`, `branch`, `base_commit`, `task`, `harness`, `timeout_sec`, `status`, `created_at_ms`, `metadata_json`

### `RunReport`

Mirrors `run_reports` table. Immutable record of what Runner observed.

Fields: `report_id`, `run_id`, `request_id`, `exit_status`, `commit_hash`, `diff_stat`, `stdout_tail`, `stderr_tail`, `metadata_json`, `created_at_ms`

## Concurrency Model

### Single-machine (v0.1, 10–20 agents)

- One Runner process, one Archetype process.
- `requests.db`: Archetype INSERTs, Runner UPDATEs claimed rows. WAL mode handles this without contention at low frequency.
- `state.db`: Runner writes only. Archetype reads only.
- `tapes/<run_id>.db`: Each file written by exactly one VM. No concurrent access.

### Multi-machine (future, hundreds of agents)

- Multiple Runner instances on different machines, each with a `claimed_by` identity.
- `requests.db` moves to a shared filesystem or is replaced by a proper queue (Postgres, Redis, etc.).
- `state.db` per Runner instance, or consolidated into a central database.
- `tapes/` directory on shared storage (NFS, S3-backed FUSE, etc.) or Runner ships files to a central location.
- The schema and row lifecycles stay the same — only the transport changes.

## Open Questions

1. **Claim-in-place vs. separate ack table?** v0.1 uses claim-in-place for simplicity.
2. **How does Archetype check out the commit for evaluation?** Clone + checkout for robustness. Workspace_path as a fast path if still on disk.
3. **Multiple reports per agent_id?** Supported by design (PK is `report_id`). Enables future partial-result reporting.
4. **Multi-runner coordination?** `claimed_by` field future-proofs, but v0.1 assumes single Runner instance.
5. **Tapes schema versioning?** Tapes proxy owns the schema. Archetype trajectory loaders should tolerate unknown columns (SELECT specific columns, not `SELECT *`).

## Risks

- **Clock skew:** ISO-8601 timestamps assume clocks are roughly synchronized. Tolerable for single-machine deployment.
- **Stale requests:** If Runner crashes after claiming but before executing, the request stays claimed forever. Archetype should implement a timeout on claimed requests (future work).
- **Workspace race:** Commit-hash capture and tapes copy must happen before cleanup. If Runner crashes between run completion and report writing, the commit may be lost. The tapes file provides a recovery path if it was already copied.
- **Schema evolution:** Adding columns to SQLite tables is safe (ADD COLUMN). Removing or renaming is not. Both sides should tolerate unknown columns.
- **Tapes file size:** Long agent sessions can produce large trajectory files. Runner should enforce a size limit or compress before copying. Archetype should handle missing tapes gracefully (agent may have crashed before any tool calls).
